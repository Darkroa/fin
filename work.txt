FINAI MT5 BROKER CONNECTION + AI TRADING WORK PLAN
==================================================

Scope
-----
Add MT5 broker accounts to the FinAPI area of the web profile. Initial broker choices:
FBS, Octa, Exness, IC Markets, XM, Pepperstone, HFM, Deriv, RoboForex, and "Other MT5 Broker".
The connection is a broker account connection, not a crypto exchange connection.

Important MT5 architecture decision
-----------------------------------
MT5 does not provide one universal REST API that can log in to every broker. FBS, Octa,
Exness, and other firms may use different MT5 server names and terminal gateways.
Therefore FinAi should not try to connect directly from the browser or pretend that
every broker has the same API.

The production design is:

1. The user opens Profile > FinAPI > MT5 Broker Accounts.
2. The user chooses the broker, enters an MT5 account number, exact MT5 server name,
   and MT5 trading password. The investor/read-only password must not be used for orders.
3. The browser sends the form over the authenticated API. It never talks directly to
   MetaTrader and never stores the password in local storage.
4. The API stores the connection server-side and returns only masked account metadata.
   The password is never returned to the UI, logs, analytics, or AI prompt.
5. A separately deployed MT5 bridge owns the terminal/EA connection. It receives
   credentials only server-to-server and translates one stable FinAi contract into
   the broker's MT5 terminal actions.
6. The bridge connects to the user's broker server, verifies the account, and reports
   health, balance, equity, margin, positions, orders, symbols, quotes, and execution
   results back to the API.
7. Until MT5_BRIDGE_URL is configured and healthy, the UI must show "Bridge pending"
   and must not invent a balance, quote, position, or successful order.

Bridge contract
---------------
The backend calls MT5_BRIDGE_URL with an optional X-MT5-BRIDGE-KEY header.
The bridge should provide these server-to-server POST endpoints:

POST /account
  Request: account_number, server, password, broker, is_demo
  Response: balance, equity, free_margin, margin_level, currency,
            open_positions, positions, last_sync_at, connected

POST /markets
  Request: account_number, server, password, broker, is_demo, query
  Response: [{ symbol, name, type, bid, ask, spread, digits, trade_enabled }]

POST /order
  Request: account_number, server, password, broker, is_demo, symbol, side,
           volume, order_type, stop_loss, take_profit
  Response: order_id, status, symbol, side, volume, fill_price, message

The bridge should use a dedicated terminal worker per account or a safe worker pool,
apply connection timeouts, reconnect with backoff, and redact all credentials.
The bridge must reject an order when the symbol is not tradeable, volume violates
broker lot rules, the market is closed, margin is insufficient, or the account is
not authenticated.

MT5 dashboard behavior
----------------------
For each saved MT5 account, show:
- broker, account mask, server, demo/live status, connection/bridge status;
- Sync button;
- balance, equity, free margin, margin level, currency, open positions;
- positions and orders after the bridge starts returning them;
- last successful sync time and a clear error state when the bridge is unavailable.

The FinAPI page must support more than one MT5 account. A label such as "Exness main"
identifies the account for AI analysis and order routing. Disconnecting one label must
not delete another MT5 account.

Market search and analysis
-------------------------
1. Search calls the MT5 bridge so the results use the user's actual broker symbols
   (for example, XAUUSD, XAUUSDm, EURUSD, or a broker-specific suffix).
2. Selecting a symbol stores the selected MT5 symbol and its latest bid/ask context.
3. Fin AI receives the symbol and available live market context through the existing
   /api/ai/chat route.
4. AI analysis must return trend, momentum, key levels, entry zone, invalidation,
   stop-loss, take-profit, risk/reward, confidence, and a statement when conditions
   are not tradeable.
5. Analysis is advisory only. Asking for analysis never places an order.
6. The AI must not guess a price when the bridge has no live quote. It should say
   that live quote data is unavailable and ask the user to retry.

AI-assisted trade flow
----------------------
1. User selects the real broker symbol.
2. User asks Fin AI for analysis.
3. User reviews the analysis and chooses buy or sell, lot size, stop-loss, and
   take-profit in the explicit trade panel.
4. The API checks the selected account, demo/live state, live-trading permission,
   symbol, volume, margin, and risk controls.
5. The UI shows a final confirmation that includes broker, account mask, symbol,
   side, lot size, stop-loss, take-profit, and demo/live mode.
6. Only after confirmation does the API call the MT5 bridge /order endpoint.
7. The result is shown with the bridge order ID, fill status, and any rejection reason.
8. Every action is audit logged without credentials: analysis request, confirmation,
   rejected order, submitted order, fill, and disconnect.

Safety and security requirements
--------------------------------
- Demo mode is the default.
- Live trading is off by default and cannot be enabled for a demo account.
- Never place an order from an AI response automatically.
- Require explicit final confirmation for every order.
- Require stop-loss and enforce maximum risk/drawdown settings before enabling
  unattended bot execution.
- Keep credentials server-side, encrypt them at rest before production rollout,
  restrict bridge access with a server-to-server secret, and rotate that secret.
- Do not expose MT5 passwords in _user_dict, browser state, logs, error messages,
  AI context, or analytics.
- Mask account numbers and server-side identifiers in the UI.
- Add rate limits and idempotency keys to order requests so browser retries cannot
  duplicate a trade.
- Treat broker connectivity as untrusted: validate every bridge response.

Current boundary
----------------
The UI and authenticated API contract are ready, but real MT5 balance, broker symbol
search, positions, and order execution require a running MT5 bridge. The current
workspace does not contain a MetaTrader terminal worker. The official MetaTrader5
Python package cannot directly log in to arbitrary MT5 broker accounts from this
Linux workspace because it requires a running MetaTrader 5 terminal.

The FinAi bridge API can still be hosted without Windows. The bridge URL is an
adapter boundary, so the backend can call:

1. A managed MT5 cloud bridge/provider that maintains the broker terminal session
   remotely and exposes account, symbols, quotes, and orders through its API.
2. A broker-specific REST, WebSocket, or FIX adapter, only where that broker
   explicitly supports the required account and trading operations.
3. A self-hosted terminal bridge on a remote Windows VPS, if the managed/provider
   route is not available.

There is no safe universal "direct MT5" REST login that works for FBS, Octa, Exness,
IC Markets, XM, and the other brokers from one Linux implementation. The app must
not pretend that a contract-only or simulated adapter is a live trading connection.
Do not enter real broker credentials until encrypted credential storage and one of
the real bridge/provider adapters have been deployed.

Next production steps
---------------------
1. Choose a real no-Windows provider adapter or a remote Windows terminal bridge.
2. Implement that adapter behind the existing `/account`, `/markets`, and `/order`
   contract; never change the frontend to send broker credentials directly.
3. Add MT5_BRIDGE_URL, MT5_BRIDGE_KEY, MT5_BRIDGE_SIGNING_SECRET, and
   MT5_CREDENTIAL_ENCRYPTION_KEY through the environment secret flow.
4. Run the selected adapter against broker demo accounts first.
5. Add an audit-log table and idempotency for orders.
6. Add integration tests for connection masking, demo orders, live confirmation,
   insufficient margin, duplicate order requests, disconnecting one account, and
   bridge timeouts.
7. Only then enable live trading for approved users and perform a staged rollout.

Implementation update — 18 August 2026 (bridge hardening)
---------------------------------------------------------
- MT5 passwords are now Fernet-encrypted before being stored in the user's connection
  JSON. Legacy plaintext MT5 records are rejected until the user reconnects them.
- FinAPI now tracks an active labeled MT5 account instead of silently routing sync,
  market search, analysis, and orders to the first account.
- Broker symbols and bid/ask quotes are loaded only from the MT5 bridge. The previous
  fallback symbol list was removed so the UI cannot suggest non-broker or fabricated
  markets.
- The MT5 dashboard now displays currency, margin level, last sync time, and returned
  open positions when the bridge supplies them.
- The bridge now runs blocking terminal calls in a worker thread and validates market
  status, broker lot rules, and available margin before sending an order. Its health
  endpoint reports `degraded` when MetaTrader5 is unavailable.
- Focused safety tests cover credential encryption, legacy plaintext rejection, lot
  rules, and closed/disabled market rejection. Frontend build and backend startup
  checks pass.

The remaining boundary is provider selection and operations: configure
`MT5_CREDENTIAL_ENCRYPTION_KEY`, deploy either a real managed/provider adapter or a
remote Windows bridge, configure the signed bridge secrets, and test against broker
demo accounts before enabling live trading.

Decision — no direct universal MT5 login from Linux
----------------------------------------------------
The FinAi backend and frontend now use the real MTAPI provider contract instead of
the old bridge-only path. MTAPI sessions are opened server-side with ConnectEx,
used for account/market/order requests, and disconnected after each operation.
The session token and password never leave the backend.
